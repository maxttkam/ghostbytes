# Contributing to GhostBytes

Thank you for taking the time to improve GhostBytes. This project handles files,
keys, passwords, and cryptographic operations, so small, reviewable changes and
clear explanations are especially valuable.

## Before You Start

- Search existing issues and pull requests before opening a new one.
- For a substantial change, open an issue first so the scope and approach can
  be discussed before implementation.
- Do not disclose security vulnerabilities, private keys, passwords, or other
  sensitive data in a public issue or pull request. Follow the reporting
  instructions in [SECURITY.md](SECURITY.md).
- By contributing, you agree to follow the project's applicable licenses and
  to communicate respectfully with other contributors.

## Development Setup

GhostBytes requires Python 3.14 or newer and uses `uv` for project and
dependency management. From the repository root:

```bash
uv sync --group dev
```

Run the application with:

```bash
uv run ghostbytes
```

The functional test runner exercises the public encryption, key-management,
hashing, randomness, and secure-delete workflows without modifying files
outside a temporary test directory:

```bash
uv run python tools/test.py
uv run python tools/test.py --verbose
```

Run the available static checks before submitting a change:

```bash
uv run pylint src tools
uv run deptry .
```

There is currently no project-wide formatter configuration. Keep the existing
style of the file you are changing, avoid unrelated reformatting, and make
sure imports and public APIs remain clear.

## AI-Generated GUI

The GhostBytes GUI is completely generated by AI. AI-generated code is not
assumed to be correct, secure, accessible, or consistent with the surrounding
application. Contributors changing the GUI are responsible for reviewing the
result as ordinary production code and documenting any material limitations.

GUI pull requests should include, where applicable:

- manual verification of the affected workflow on the supported platforms;
- tests for the behavior behind the interface, not only screenshots or visual
  checks;
- review of focus order, keyboard access, readable error messages, and layout
  behavior at practical window sizes; and
- explicit review of any path that displays, accepts, stores, deletes, or
  transforms passwords, keys, plaintext, or encrypted files.

Do not accept an AI-generated suggestion without understanding its control flow,
error handling, dependencies, and security implications.

## Issues

Use GitHub issues for reproducible bugs, focused feature requests, and questions
that are useful to other users. A useful issue includes:

- a concise description of the expected and actual behavior;
- exact reproduction steps, including the operating system and Python version;
- the smallest relevant log or traceback, with secrets and personal data
  removed; and
- context about whether the issue affects files, keys, configuration, or
  compatibility.

Do not use public issues for suspected vulnerabilities. See [SECURITY.md](SECURITY.md).

## Branches and Commits

- Create a focused branch from the current default branch.
- Keep each branch and commit limited to one coherent change.
- Use a clear imperative commit subject, such as `Improve key import errors`.
- Do not commit virtual environments, caches, generated build output, private
  keys, passwords, test secrets, or user data.
- Rebase or update your branch as needed so the pull request can be reviewed
  against the current base branch.

## Pull Requests

Pull requests should explain the problem, the chosen approach, and any
trade-offs or compatibility implications. Include screenshots or command
output when a user-facing workflow changes.

Before requesting review, confirm that:

- the change is scoped and the relevant tests pass;
- new behavior has focused tests where practical;
- user-facing behavior, configuration, or security documentation is updated;
- error paths and failure behavior are covered, not only the happy path;
- the pull request description calls out migrations, limitations, or follow-up
  work; and
- the branch contains no sensitive data or unrelated formatting changes.

Maintainers may request revisions, additional tests, or a smaller change before
merging. Keep review discussions focused on the code and respond to feedback
with updated commits or a clear explanation.

## Security-Sensitive Changes

Changes involving encryption, decryption, key generation or storage, password
handling, random-number generation, hashing, file deletion, or dependency
updates require extra care:

- explain the security rationale and identify the affected data or threat;
- prefer established library primitives over new cryptographic constructions;
- include negative tests for invalid, tampered, truncated, or incompatible
  input where applicable;
- avoid logging passwords, private keys, plaintext, or complete ciphertext;
- document compatibility and recovery implications before changing formats or
  configuration defaults; and
- request review from a maintainer familiar with the affected security area.

Do not quietly fix or disclose a suspected vulnerability through a normal pull
request. Coordinate privately using the process in [SECURITY.md](SECURITY.md).

## Documentation and Tests

Update documentation when a change affects installation, commands, supported
platforms, algorithms, configuration, file formats, or user-visible behavior.
Tests should be deterministic, isolated, and safe to run on a development
machine. Destructive operations must use temporary fixtures and must not target
real user data, free space, or mounted production volumes.
